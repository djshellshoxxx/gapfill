# W-01 / W-02 Windows editor-automation crash: status (gap-closing pass, 2026-10-21)

Status: **open, external.** The ticket (`docs/dev/features/W-01-windows-editor-automation-crash.md`) is a Windows-only
investigation: pluginval at strictness level 10 crashes during editor automation on a Windows host (issue #13). It needs a
Windows machine or runner, a crash dump and symbols (`RelWithDebInfo` with PDBs). None of those exist in the Linux
sandbox this pass ran in, so there is **no reproduction, no stack trace, no root cause and no fix** here, and none is claimed.

## What was done in the repository

* Read the code paths named by the ticket's hypotheses. Observations only; none of them is a proven cause:
  * H1 destruction order: `GapFillLookAndFeel lookAndFeel` is declared before the panels and attachments in
    `PluginEditor.h`, so it is destroyed after them; `~GapFillAudioProcessorEditor` calls `setLookAndFeel (nullptr)` as its last
    statement. Looks consistent with the safe pattern on Linux; unconfirmed on Windows.
  * H2 timers: the editor and `WaveformGapView` call `stopTimer()` first in their destructors; `FineSlider` and `FlashButton`
    have no destructor of their own and rely on the `juce::Timer` base class. A full audit of every `Timer` subclass was not done.
* **2026-10-30:** step 3 (Linux part) added as `EditorLifecycle.editor_create_destroy_while_automating_and_processing` (`Tests/features/TestEditorLifecycle.cpp`): 40 rounds of editor create / resize / destroy on the test thread while a second thread calls `setValueNotifyingHost` on random parameters and a third runs `processBlock`. **Result: green** (1 passed, 0 failed, 33 s, Linux Release under Xvfb, local run). No defect reproduced, so no fix was made and no hypothesis is confirmed or ruled out for Windows. Limits: the message loop is not pumped (`JUCE_MODAL_LOOPS_PERMITTED=0`) so AsyncUpdater / timer callbacks queued by the automation thread are never delivered to a live editor; no ASan / TSan build was run (a `-fsanitize=thread` build of `GapFillTests` is the next Linux step); one run only.
* The Linux-reproducible parts of the minimised test already existed: `History.recipe_drawer_is_hosted_clicks_pass_through_and_survives_reopen`
  creates and destroys the editor three times, and the Q-01 harness has a `gui-lifecycle` step that runs it. They do not
  automate parameters from a second thread.
