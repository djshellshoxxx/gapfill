## Compatibility refinement

Existing `coopMode` and `coopGroup` must retain their old choice counts **and**
integer values. Appending an enum choice changes normalized host automation:
old mode 0.5 maps to Alternate, but four choices would map it to Follow. Therefore
do not append public choices to either released parameter. The internal engine
may use Deterministic=3, selected through new tail-group parameters instead.

Proposed COOPEXT tail parameters, centrally registered after the released FM10
tail and other coordinated extension groups:

| ID | Type/default | Behavior |
|---|---|---|
| `coopDeterministic` | bool, false | Select new deterministic engine; false retains exact legacy modes. |
| `coopDetGroup` | Use legacy group, A–H; default Use legacy group | Does not alter the released group parameter's normalization. |
| `coopSlot` | integer 1–32, 1 | Stable musical identity, distinct from a process lifetime token. |
| `coopPriority` | integer percent 0–100, 50 | Weighted ownership; zero retains the specified small floor weight. |
| `coopYield` | percent 0–100, 70 | Reduces non-owner density/fill, never increases either. |
| `coopGrid` | Beat/Two beats/Bar/Two bars/Four bars, Bar | Shared election time grid. |

Group, slot and grid are not automatable. Every new ID is performance state,
excluded from Random/Surprise/Undo and scene capture. All old parameter IDs,
indices, ranges and saved integer/normalized values stay unchanged.

## Completed pure-model slice

`Source/features/coop/Deterministic.h` provides immutable bounded snapshots,
validation, weighted rendezvous ownership, musical slot calculation and yield
scales. Election uses the existing permanent co-op salt, musical group/time-slot
and fixed member slots. Runtime lifetime tokens, array order and thread order are
not random inputs. Tokens still detect duplicated/recycled membership records.

- Exactly one owner over 64 bars for four equal members; Yield100 gives every
  non-owner zero density.
- 2,000-slot priority shares within three percentage points of 10/20/30/40%.
- Removing a non-owner leaves ownership unchanged.
- Changed runtime tokens and reversed input membership order leave election unchanged.
- One/four threads and 64/512-block decision-position reconstruction agree.
- Invalid/duplicate membership rejected; negative pre-roll and 7/8 grid tested.
- Yield is neutral for owners and bounded/reducing for non-owners.

## In progress / integration contracts

- Separate bounded deterministic registry; preserve the existing legacy registry
  layout/capacity and behavior. Packed lifetime records must publish atomically;
  no processor pointers, token reuse or partial records.
- Coherent versioned roster proposals with shared future musical activation.
  Register callbacks' complete admitted ranges before a proposal becomes visible,
  so no callback has already rendered across a newly published boundary.
  Retain previous/current snapshots until every live member no longer needs the
  previous version; use bounded retries and a visible fail-closed diagnostic.
- Production decision hook applies non-owner yield before the probability roll,
  and rejects at Yield100 without advancing new RNG state.
- New group recall carries generation, scene index, exact common PPQ deadline and
  cancellation/membership generations. It never sends pointers to another instance.
  `SceneController::gotoSceneAt` resolves the receiving instance's bank locally;
  late/invalid adoption must cancel, not fall back to a different boundary.
- GUI/Help/ParamInfo, duplicate-slot repair, group status and capacities.

Still unverified: registry concurrency and teardown, all production hooks, native
builds, allocation guard, TSan, multi-instance rendered audio, MIDI/group scenes,
host process-isolation fallback, reference CPU and audible behavior. Keep these
requirements open until their own retained evidence exists.
